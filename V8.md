# v8

Breaking changes waiting for the next major release. Every published crate shares the 7.x
line, and Cargo treats any 7.x as compatible with any other, so anything here would break
an adopter's `cargo update` if it shipped sooner. `mise run lint:semver` catches the ones
that reach a pull request.

When a change can't go out without breaking the public API, ship the part that doesn't
break now and add the rest here: what changes, why, and what adopters should do.

## Smaller flag and command tables

Binary size work on the oxc CLIs (oxlint and oxfmt) found that the derive-emitted tables are
now the largest remaining usage cost: about 22 KB of data plus about 11 KB of relative
relocations in oxlint, roughly 550 bytes per flag. They are large because every field is a
fat reference or a `u64`, and each reference needs a relocation in a position-independent
binary.

- **What changes:** `Flag` and `FlagMeta` (and the matching command tables) store offsets into
  one shared string table, with narrower integers for `key`, counts and indices, instead of
  `&'static str`, `&'static [..]` and `u64` fields.
- **Why it breaks:** those fields are public, so changing their types breaks any code that
  builds or reads a table by hand. Derived code is unaffected.
- **Estimated saving:** about 4 KB on oxlint from `FlagMeta` alone, more once `Flag` follows.
- **What adopters do:** nothing if they use the derives. Hand-written tables regenerate or
  move to the constructor functions.

## Per-flag binding type names

The derive emits a `FLAG_<n>_BINDING_TYPE` function returning a type name string for every
flag, stored in the public `Flag::binding_type: Option<BindingType>` field. Only derive-generated
code reads it: it compares two flags' binding types to decide whether a child command's
redeclaration of a global flag is compatible. `Parser` never reads it.

- **What changes:** `Flag::binding_type` and the `BindingType` type are removed, and the
  derive checks redeclaration at expansion time instead, so the per-flag function and string
  are no longer emitted. Estimated saving: one function and one string per flag.
- **Why it breaks:** both are public. Any code that names `BindingType` or sets or reads
  `Flag::binding_type` stops compiling, and a hand-built `Flag` literal that sets the field
  does too.
- **What adopters do:** nothing if they use the derives. A hand-built `Flag` drops the
  `binding_type` field. Redeclaration compatibility for hand-built trees is then not checked,
  because only the derive has the type information.

## Compile-time parser specialization

`Parser::with_action_errors` carries the `default_flag_route` and sigil-argument logic that only
some CLIs use, roughly 5 KB per binary. Dropping it where unused means making `Parser`
generic over a const set of behaviours that derives choose.

- **What changes:** `Parser` gains const generic parameters. Giving them defaults keeps
  `Parser<'t, 'a, 'v>` written in a type position compiling, and values built through
  `Parser::new` infer them, so most callers need no change.
- **Why it breaks anyway:** a new generic parameter on a public type is a major change to
  `cargo semver-checks`, and anything that names the type in a position without defaults, such
  as an `impl` block or a trait implementation for `Parser`, has to spell the parameters.
- **What adopters do:** nothing for code that only constructs a `Parser` and calls
  `next_event`. Code that implements traits for `Parser` or stores it in a struct with an
  explicit type adds the new parameters, or the defaults.
